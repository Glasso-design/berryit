## Verifieringskedja

Berättelse: behörig administratör väljer produkt/projekt/ägare, skapar ett
idempotent jobb och ser serverworkerns verifieringsunderlag och blockerare.

| Gräns | Evidens |
|---|---|
| UI → syntetisk RPC-transport → SQL | Factory-browsertest passerar; formulär skapar verkliga isolerade SQL-rader |
| Direkta RPC/RLS-anrop | Nekad anon, saknad MFA, IT Support/Developer utan separat permission, fel organisation/projekt/ägare och direkta tabellskrivningar |
| Dynamiska roller | Separat projektscope med factory.read/create fungerar; avstängd/utgången/återkallad rättighet upphör vid nästa kontroll |
| SQL → worker/provider | Två workers, förlorad lease, processavbrott, timeout efter commit och stabil resursidentitet testade |
| Worker → UI | Progress/checklista visas; tekniska rutor kan inte manuellt förfalskas; oanslutna produkter blockeras |
| Stängd webbläsare | Samma jobb färdigställs av worker utan öppet fönster; MOCK READY visas som SIMULATED |
| Faktisk produkt | Två rena DB/runtime-instanser; fyra webbinloggningar mot verklig QABGO HTTP; främmande token/DB-credential nekas |
| Full Supabase/SSO | Ej verifierad i detta pass: teststacken här är fristående PostgreSQL/Core, inte GoTrue/PostgREST/Storage |

## Produktions- och expansionsgrindar

1. Behåll QABGO `ADAPTER_IN_DEVELOPMENT`. Godkänn en signerad distributionsbundle,
   releaseversion, lokal admin-overlay och neutrala verksamhetsinställningar.
2. Förbered separat godkänd komplett Supabase-/SSO-testmiljö. Verifiera riktig
   bearer/session/GoTrue/TOTP, PostgREST-EXECUTE/RLS och Storage genom HTTP.
   Tidigare isolerade serverstackar har inte ändrats eller antagits saknas.
3. Granska serverdeployment/workeridentitet och secret-store, återkallelser,
   provider-intents/outbox och roll-/MFA-flöde genom faktisk anslutningsväg.
4. Bekräfta Tenant-partner/unit eller berättigad standalone-identitet/kvot,
   alternativt uttryckligen valt managed-resource-konto. Ingen fallback.
5. Godkänn provider-/region-/runtimekapacitet, domänägarskap, DNS/TLS, faktiska
   kostnadsestimat, budgettak, R2-IAM och multipart/HEAD/list-avstämning.
   Produktens verkliga R2-uppladdningsvägar behöver anslutas till den centrala
   kvotbrokern före drift; kvotprovet här gäller Factory:s lokala objektprovider,
   inte att QABGO redan använder R2. Produktens databaslagring är separat.
6. Välj/verifiera e-postmodell, destinationer och SPF/DKIM/DMARC för vald sändare.
   Routing räknas inte som mailbox eller transaktionsleverantör.
7. Anslut godkänd extern krypterad backup, separata recoveryidentiteter och
   återställningsövning. Tidigare PASS 3D-A-manifest är BLOCKED för behörighet/
   overifierad diskhälsa; inget antas installerat eller färdigställt här.
8. Företags-/åkeriuppgifter, godkänd prismodell och eventuella betalavtal måste
   verifieras separat. Inga pilotpriser, verkliga avtal eller kunddata kopieras.
9. Kör godkänd stagingresa med två ägare, realistisk last, provider-reconciliation,
   R2-isolering, transport-TLS och produktbackup före nytt produktionsbeslut.

Prioritera VISI efter godkänd Auth/Storage/residensmall. HQ/ARENAHUB behöver
säker produktmappning före adapter. Spel och desktopbundna produkter står kvar
som NOT_PROVISIONABLE. En QABGO-adapter gör inte övriga produkter färdiga.
